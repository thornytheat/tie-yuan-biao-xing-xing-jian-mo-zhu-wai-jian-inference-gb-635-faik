# 会员撤回授权 · 按会员清除（M8）设计与操作规程

会员撤回授权后，应用侧保存的**姓名、手机号、会员号原值**不再保留；但历史批次的
**键关系判断与计数依据**仍须可核验，订单金额等度量不能丢。本文件是 M8 的唯一规则来源，
代码（`app/modules/m8_erasure/`）、接口与测试都引用这里的定义。

## 1 清除对象与保留对象

| 分类 | 字段 / 数据 | 处理 |
|---|---|---|
| 原值（必须抹除） | `odl_member.member_name`、`odl_member.phone`、`odl_member.member_id`（会员号本身也是可识别原值） | 样本值字段置空并记脱敏，不留原值、不留可逆映射 |
| 引用原值 | `odl_sale_order.member_id` 等子表外键列里该会员的取值 | 同列清除；订单行本身、`order_amount` 等度量全部保留 |
| 核验凭据（必须保留，且不含原值） | 行级盐化哈希、清除计数、键判定的聚合数值（去重数/计数行/包含度/基数比）、金额合计 | 原样保留 |
| 不受影响 | 其他会员的全部数据、与该会员无关的表/列/批次结论 | 一个字节都不改 |

会员号之所以也算原值：它是 DDL 声明的主键，样本值直接落库，能直接定位自然人，
撤回后不允许再以明文出现；需要「这个人曾经存在、这些订单属于同一主体」的核验能力时，
只允许通过**盐化哈希**完成，哈希不可逆推出会员号。

## 2 不可逆凭据：盐化哈希

- 算法固定 `sha256`，输入 = 领域前缀 `starmodel:member:v1:` + 会员号归一值 + `:` + 盐。
- 盐只在本次清除请求由 `secrets.token_hex(32)` 生成，存入清除登记，**不导出、不进接口响应**；
  没有盐就无法用候选会员号字典反推哈希，因此凭据本身不含原值、也不可直接重识别。
- 同一清除单内所有批次、所有表统一用同一盐，跨批次核验「同一主体」时比的是哈希；
  不同清除单的盐不同，两张清除单之间无法用哈希互相串联。
- 哈希只存十六进制串，不存生成它的会员号。

## 3 清除范围（按批次 × 表 × 列扫描，不整批抹除）

对库内**每一个历史批次**独立执行，扫描以下落库位置：

1. `columns_meta.sample_value`：列样本原值。仅清除受影响列（会员主体表的姓名/手机号/会员号，
   以及引用该会员号的外键列）；清除前把原值的盐化哈希、长度、字符类指纹记入凭据，再置 `''`。
2. `columns_meta` 的统计与证据 JSON：`distinct_count`、`null_rate`、`unique_rate`、
   `evidence_json` 里的聚合数值**不动**——它们是键关系判断与计数的核验依据；
   只在证据里追加 `erasure` 段（哈希、清除格数），不写原值。
3. `quarantine.raw_value` / `detail`：隔离记录逐行扫描，凡出现该会员姓名/手机号/会员号
   原值的，原值替换为 `〔已按授权撤回清除〕` 占位，并把原值哈希留痕；不含原值的隔离行不动。
4. `conflicts`（冲突表）的 `key_value`、`kept_json`、`dropped_json`：同样逐字段扫描替换。
5. `key_findings.evidence_json`、`star_objects.evidence_json`：只含聚合数，不含会员原值；
   不修改（防御性扫描确认无原值，若发现则按隔离记录同规则处理）。
6. `totals`、`row_ledger`、`stages`、`manifests`、`tables_meta`：计数与清单，不含会员原值，
   金额合计（`metric_total`、`metric_sums`）原样保留。
7. 导出：M8 只改库内已落库数据；所有导出接口（列规格 CSV、证据 CSV、隔离 CSV、冲突 CSV、
   清单 JSON、页面）都从库读，清除后导出件天然不含原值，且无需单独清理历史文件
   （本系统不落导出文件，导出按请求现生成）。

## 4 断点续跑与清除单状态

清除按「清除单（erasure request）」组织，一单一会员，状态机：

```
running ──全部批次扫描并提交成功──▶ done
   │
   └──任一阶段异常──▶ interrupted（已提交的批次不回滚，凭据已落库）
                      │
                      再次调用同一会员的清除 ──▶ 从首个未完成批次接着跑 ──▶ done
```

- 清除单主键 = 会员号的盐化哈希（不含会员号本身），另存人类编号 `ER-yyyyMMddHHMMSS-xxxx`。
- 每个批次一个 `erasure_unit` 工作单元，状态 `pending/running/done`；进度表记录
  `(request_id, batch_id, stage)` 水位。续跑只挑 `pending/running` 的单元，`done` 的跳过。
- 每个批次的清除在**单事务**内提交（沿用 Store 的事务约定），中断不会留半批。
- 清除完成前的读保护：清除单处于 `running/interrupted` 且涉及某批次时，该批次中受影响列的
  原值读取接口直接拒绝（409 `E_ERASURE_IN_PROGRESS`）；聚合数、金额、其他列正常可读。

## 5 重放防回灌

- 撤回生效后，清除登记写入一条**抑制规则**（按会员号哈希，不存原值）。
- 此后再跑接入（含旧样本文件原样重放）：M1→M4 流水线照常计算聚合数，但落库前 M8 过滤层按
  抑制哈希比对，受影响会员的姓名/手机号/会员号原值一律不写入 `sample_value`、隔离/冲突原值字段，
  写占位与哈希凭据。旧样本重放不会把原值带回任何批次。
- 同一 `batch_key` 的幂等复用逻辑不变：已清除批次复用的是已清除的落库结果，也不含原值。
- 抑制规则对其他会员不命中，其数据正常落库、正常展示。

## 6 幂等：重复执行不新增凭据

- 同一会员重复调用清除：若清除单已 `done`，直接返回原清除单与既有凭据，
  返回 `E_ERASURE_IDEMPOTENT` 提示，不新建清除单、不新增凭据行、不重复计清除格数。
- `interrupted` 续跑：只处理未完成单元，已完成单元的凭据不重复生成。
- 凭据按 `(request_id, batch_id, table_name, column_name, value_hash)` 唯一约束，
  重复提交在数据库层即被挡下。

## 7 可核验性：清除后还能验证什么

清除后审核员可凭以下不含原值的材料复核：

1. 清除凭据 CSV/JSON：每一条给出批次、表、列、行定位（`row_ref`）、原值盐化哈希、
   原值长度与字符类指纹、清除时间、清除单编号——证明「某位置确实有过一个值且已清除」，
   但无法还原该值。
2. 键判定聚合数未变：`key_findings` 的去重数/计数行/包含度/基数比与清除前快照一致，
   证明键关系结论的计数依据没有被清除动作破坏。
3. 金额未变：`totals.metric_total` 与事实表度量合计清除前后逐分相等。
4. 清除前后数据库全库原值扫描报告：清除后扫描受影响会员的姓名/手机号/会员号，命中数为 0。

## 8 接口

| 方法路径 | 作用 |
|---|---|
| `POST /api/erasure/members` | 提交/续跑会员清除，body `{"member_id": "0071"}`；幂等 |
| `GET /api/erasure/requests` | 清除单列表（不含盐、不含原值） |
| `GET /api/erasure/requests/{request_id}` | 清除单详情、逐批次进度、凭据计数 |
| `GET /api/erasure/requests/{request_id}/evidence.csv` | 清除凭据导出（盐化哈希，无原值） |
| `GET /api/erasure/page` 页面 | 清除台：提交、进度、凭据查看 |
